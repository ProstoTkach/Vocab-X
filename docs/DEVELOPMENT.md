# VocabX — для розробників

Технічний опис проєкту: запуск, структура, ключові рішення. Опис застосунку для користувачів — у [README](../README.md).

> Статус: **фаза A, етап A5** — одна велика колода за ступенем забування (без денних лімітів),
> повторення в оболонці застосунку, колоди й слова (створення, підказки перекладів, порядок,
> архів, повторення окремої колоди), налаштування навчання, онбординг, панель зсуву часу.

## Запуск

Потрібні Node.js ≥ 22 і pnpm (`npm i -g pnpm`).

```bash
pnpm install
pnpm dev           # http://localhost:3000 → /uk
pnpm typecheck     # TypeScript у всіх пакетах
pnpm lint          # ESLint, зокрема власні правила дизайн-системи та i18n
pnpm test          # Vitest (ядро, дані, теми, переклади, правила лінтера)
pnpm build         # production-збірка Next.js
pnpm e2e           # Playwright: усі тести, мобільний (390×844) і десктопний (1280×800) в'юпорти
pnpm e2e:changed   # лише тести того, що змінилося (див. нижче)
pnpm screenshots   # скріншоти /dev/ui і сторінок у 5 в'юпортах × 5 тем → apps/web/screenshots
```

Перед першим `pnpm e2e`: `pnpm --filter @vocabx/web exec playwright install chromium`.

**Вибіркові e2e-тести.** `pnpm e2e:changed` дивиться, які файли змінено (ще не закомічені, або
`--base main` — усе, чим гілка відрізняється від `main`), і запускає лише тести, що їх
покривають: карта «шлях → тести» — у `apps/web/scripts/e2e-changed.mjs`. Якщо змінився будь-який
інтерфейс (`.tsx`, `.css`, переклади, `public/`), додається `smoke.spec.ts`: кожна сторінка
відкривається без помилок у консолі й без горизонтальної прокрутки. Зміни налаштувань тестів
(`fixtures.ts`, конфіг Playwright, залежності) запускають усе. `--list` лише показує, що піде в
прогін. Перед пушем — повний `pnpm e2e`. Звук у тестовому браузері вимкнено: `--mute-audio` і
`NEXT_PUBLIC_SILENT_SPEECH=1` — системний голос Windows прапорця браузера не слухає, тож тестова
збірка вимовляє слова з нульовою гучністю.

Сторінка `/uk/dev/ui` показує всі компоненти в усіх темах. Вона доступна в `pnpm dev`;
у production-збірці — лише з `NEXT_PUBLIC_ENABLE_DEV_UI=1`.

**Режим розробника — за кодом.** Налаштування → «Режим розробника» питає код; його перевіряє
сервер (`/api/dev-unlock`, змінна `DEVELOPER_CODE` — лише на сервері, у браузер не потрапляє).
Відкритий режим (`AppSettings.devUnlocked`) дає перемикач «Панель розробника» (зсув часу,
способи навчання; Ctrl+Shift+D) і **полігон способів навчання** (`/review/lab`: той самий екран
повторення, спосіб і рівень — зі списків, слова по колу, нічого не зберігається й не йде в
статистику). Браузер, що відкрив режим, у статистиці позначається як внутрішній. Тести
Playwright запускають сервер із `DEVELOPER_CODE=test-code`. Сам код інструментів є в збірці;
закриває їх саме код, а не збірка (дані все одно лише локальні, на сервер вони не впливають).

## Структура

```
apps/web                 Next.js (App Router), Tailwind CSS v4, next-intl, Radix UI
  messages/<locale>/     переклади інтерфейсу (ICU), один JSON на простір імен
  src/app/[locale]/      маршрути; (app)/ — сторінки в оболонці, dev/ui — галерея компонентів
  src/components/ui/     Button, Card, Dialog, Tabs, Switch, ProgressBar, Toast, Avatar, Badge, Tooltip
  src/components/shell/  нижня панель (телефон), бічна панель (md+), колонка прогресу (lg+)
  src/themes/            реєстр тем і токени кольорів
  src/i18n/              реєстр локалей, маршрутизація, завантаження повідомлень
packages/core            чисті функції: FSRS-6, XP, стопка, оцінювання відповіді, журнал подій,
                         інтерфейси репозиторіїв, Clock/Rng, параметри моделі (src/config)
packages/content         реєстр мов, мовні адаптери, вбудовані колоди (src/decks/*.json)
packages/data            реалізації репозиторіїв: LocalStorageRepo (фаза A)
tools/eslint-plugin-vocabx  правила: design-tokens, no-jsx-literals
reference/               еталонні файли, з яких перенесено ядро
```

`core` не залежить від браузера чи Node: той самий код працюватиме на сервері у фазі B.

## Ключові рішення

- **Журнал подій — джерело істини.** Стан картки відтворюється з подій функцією `replayCard`;
  випадковий зсув інтервалу береться з `Rng`, засіяного `id` події, тож відтворення детерміноване.
- **Параметри моделі** (`w₀…w₂₀`, `ρ`, `τ⁰`, ліміти, пороги оцінювання, XP) — лише в
  `packages/core/src/config/params.ts`. Відхилення від класичного FSRS-6 (фаза вивчення в хвилинах,
  відновлення складності, бонус за серію, ранні успіхи у фазі вивчення) описано в шапці
  `packages/core/src/scheduler.ts`.
- **localStorage**: ключі `vocabx:v1:*`, `schemaVersion` з міграціями, компактний журнал,
  `StorageQuotaError` при переповненні, експорт/імпорт JSON з відкатом. UI звертається до даних
  лише через `useRepos()`; лінтер забороняє `localStorage` у компонентах.
- **Теми — набори семантичних токенів.** Стандартну палітру Tailwind вимкнено (`--color-*: initial`),
  тож `bg-white` чи `text-gray-900` не існують; правило `vocabx/design-tokens` додатково ловить
  сирі кольори, `dark:` і фізичні напрямки (`ml-`, `left-`, `text-right`). Тема застосовується
  inline-скриптом у `<head>` до гідратації — без «блимання».
- **Жодних рядків у JSX.** Правило `vocabx/no-jsx-literals` ловить текст і текстові атрибути
  (`aria-label`, `alt`, `placeholder`…). Тест перевіряє, що всі локалі мають однакові ключі й
  коректний ICU з тими самими аргументами.
- **«Назад» закриває вікна.** `useCloseOnBack` (`apps/web/src/lib/close-on-back.ts`) кладе в
  історію додатковий запис з тим самим URL, поки відкрите вікно; «Назад» знімає його й закриває
  вікно. `Dialog` і `Popover` з `components/ui` роблять це самі (крім `dismissible={false}`).
  Вікно, закрите кнопкою, прибирає свій запис кроком назад; якщо разом із закриттям застосунок
  переходить на іншу сторінку (`useRouter` з `@/i18n/navigation` про це повідомляє), нова
  сторінка займає місце запису — інакше крок назад скасував би перехід.
- **Доступність.** Контраст токенів кожної теми (WCAG AA) перевіряє unit-тест; сторінки — axe у
  Playwright. Цілі натискання ≥ 44 px, логічні властивості для RTL.

## Як додати тему

1. Файл `apps/web/src/themes/<id>.ts` з усіма токенами з `COLOR_TOKENS` і полем `unlock`
   (`free` | `level:N` | `achievement:id` | `purchase:sku`).
2. Запис у масиві `THEMES` у `apps/web/src/themes/registry.ts`.
3. Назва теми — ключ `<id>` у `messages/<locale>/themes.json` для кожної локалі.

`pnpm test` перевірить контраст усіх пар токенів.

## Як додати мову інтерфейсу

1. Папка `apps/web/messages/<code>/` з тими самими JSON-файлами, що й `uk/`.
2. Запис у `LOCALES` у `apps/web/src/i18n/locales.ts` (`dir: 'rtl'` для арабської, івриту тощо;
   `script` обирає резервний стек шрифтів).

`pnpm test` перевірить, що ключі й аргументи збігаються з українською локаллю.

## Колоди та велика колода

Повторюється одна велика колода: слова з усіх активних власних колод мови, від найбільш забутих.
Колоди лише визначають, що до неї входить: архівна колода — на паузі, а будь-яку колоду можна
повторити окремо (`/review?deck=<id>`). Денні ліміти необов'язкові й за замовчуванням вимкнені.
Де розгорнута бічна панель — задає `apps/web/src/components/shell/sidebar-config.ts`.

## Як додати вбудовану колоду

1. JSON-файл у `packages/content/src/decks/` (формат — `DeckFile` у `decks/index.ts`): слова з частиною
   мови, перекладами за кодом мови та прикладами.
2. Запис у `DECK_FILES`. `pnpm test` перевірить унікальність лем, наявність перекладів і те, що
   приклад містить слово.
3. Тематична колода (не рівнева A1–C2) має поле `topic`; рівень `cefr` — типовий для теми (для
   сортування в бібліотеці). Тест рівня тематичні колоди не використовує.

Тест рівня бере слова з двох фіксованих списків на кожен рівень (перша спроба й повторна, без
спільних слів): `packages/content/src/placement.ts`. У списку — слова, що задаються спершу (A1 3,
A2 4, B1 5…), і ще 3 на випадок помилки. Неправильні варіанти — з решти слів колоди рівня.

Переклади нових слів, які додає користувач, підказують Google Translate і Wiktionary (переклади),
Wiktionary та Free Dictionary (частина мови, приклади) — з тайм-аутом, кешем і ручним введенням як
запасним варіантом (`apps/web/src/lib/lexicon`). Google Translate (Cloud Translation API v2)
викликає сервер — `/api/translate` — від імені того самого сервісного акаунта Google
(`GOOGLE_CLIENT_EMAIL`, `GOOGLE_PRIVATE_KEY`, `GOOGLE_PROJECT_ID`); у проєкті Google Cloud має
бути увімкнено Cloud Translation API. Без цих змінних переклад просто не підказується.

Ліміти `/api/translate` (крок 2.1a): без входу — 30 слів на добу з однієї адреси відправника
(одне «Знайти» питає до 3 слів: саме слово й 2 синоніми, тож це щонайменше 10 використань), з
входом — 300 на акаунт (щонайменше 100). Понад ліміт — 429 `{ limited: 'anonymous' | 'account' }`
і `Retry-After`; форма слова пише, що підказки на сьогодні закінчилися, і без входу пропонує
увійти, а до кінця очікування більше не питає сервер. Перед базою — ліміт у памʼяті інстансу
(20 на хвилину з адреси), щоб потік запитів не будив Neon. Відповіді Google спільні для всіх і
лежать у `translation_cache` 30 днів (стільки ж, скільки раніше в CDN; умови Google щодо зберігання
перевіряє крок 6.7). Стеля для всіх — `TRANSLATE_DAILY_CHARS` символів на добу, рахуються лише
слова, що пішли до Google; понад неї й без бази — 503, до Google нічого не йде.

## Режим «Речення» і приклади

Ядро — `packages/core/src/sentence.ts`: `clozeOf` знаходить слово в прикладі (саме слово, лему,
варіант або форму: для англійської — правильні закінчення, щоб «convenience» не вважалось
формою «convenient»; для інших мов — основа без двох останніх літер і коротке закінчення);
`clozeForReview` бере приклад за числом відповідей картки (`reps`), тож вони чергуються, а
помилка (рівень не знижується: `mistakeKeepsLevel` у параметрах планувальника) приводить інше
речення. Кожна правильна відповідь у реченнях — наступний рівень (3 → 1), без умов
планувальника про паузу й стабільність: рівні речень рахує `applyEvent`
(`packages/core/src/events.ts`). Формати `SENT_PICK`, `SENT_SAY`, `SENT_TYPE` дописані в
кінець `ALL_FORMATS`.

## Змішаний режим

Режим за замовчуванням (`AppSettings.mixedMode`; `quizMode` і `sentenceMode` мають перевагу,
усі три вимкнені — картки). Коло кроків — `MIXED_STEPS` у `packages/core/src/types.ts`
(q1 s1 q2 q3 s2 s3). Крок слова — `CardState.mix`, помилки поспіль на ньому — `misses`; без
кроку (нове слово чи відповідь в іншому режимі) його дає рівень (`mixedStepOf`). Відповідь у
змішаному режимі позначена в журналі `kind: 'mixed'` (у стиснутому записі — прапорець `2` у
кінці кортежу), тож повторне відтворення журналу дає ті самі кроки; відповідь в іншому режимі
крок скидає. Правильна — крок уперед (після шостого — перший), дві помилки поспіль — крок
назад. Слово без прикладу на кроці речення питається тестом того ж рівня.

Слово зберігає до `MAX_EXAMPLES` (5) прикладів. Вбудовані колоди мають по одному: писати ще по
чотири для кожного з ~450 слів означало б ~1 800 неперевірених речень, які щоразу завантажувалися
б у браузер кожного користувача, хоча більшість слів ніхто з них не дійде до речень. Натомість
`useExampleTopUp` (`apps/web/src/lib/lexicon/example-top-up.ts`) у режимі «Речення» у фоні шукає
приклади для слів поточного повторення, яким їх бракує (до 10 слів за сесію, по одному запиту, з
кешем словників), і зберігає знайдене разом зі словом. Слово без жодного придатного прикладу
питається як тест із 4 варіантів.

Тури сторінок — `components/tour/page-tour.tsx` (геометрія спільна з туром головної:
`components/tour/geometry.ts`): кроки з позначками `data-tour`, тексти — `messages/*/tours.json`,
що бачили — `lib/home-tour.ts`. Крок із `hidden: true` (і в турі головної) пропускається, але
лишається в коді разом із текстами; тур без жодного видимого кроку не показується. Підказка
до «Знайти» у вікні «Додати слово» — `Tooltip` з `long`: після довгого наведення (900 мс) або
довгого натискання на сенсорному екрані (500 мс; таке натискання кнопку не натискає).

Розмір тексту застосунку — `AppSettings.fontScale`: boot-script ставить `font-size` на `<html>`
до першого показу, `applyFontScale` — одразу після зміни; усе в rem, тож масштабується
весь інтерфейс. Слово на картці (`Term` з `fit`) вимірюється: зменшується лише тоді, коли не
вміщається в рядок. Тест рівня додає перші `ONBOARDING_DECK_WORDS` (15) слів колоди. Полігон тримає три останні відповіді для
«Скасувати»; змішаний режим на полігоні йде кроками по черзі, без вибору рівня.

`clozeOf` вирізає кожне входження слова (`parts` і `answers`). Полігон (`/review/lab`) — це
`ReviewSession` з `lab`: спосіб і рівень задаються списками, `grade` лише переносить картку в
кінець стопки, нічого не пише в сховище й не надсилає подій.

Розпізнавання мови — Web Speech API (`apps/web/src/lib/speech-recognition.ts`), без запису на
стороні застосунку.

## Як додати формат вправи

1. Рендерер у `apps/web/src/components/review/formats/`: компонент, що отримує `FormatProps`
   (`card`, `side`, `typing`, `onTypedSubmit`…) і малює лише вміст картки, та об'єкт
   `FormatRenderer` (`format`, `supportsTyping`, `frontText`).
2. Запис у масиві в `formats/registry.ts`. Оболонка `ReviewSession` (прогрес, оцінки, свайпи,
   клавіші, скасування, підсумок) не змінюється.

## Демонстрація інтервального повторення

У режимі розробника (див. вище) «Панель розробника» (або Ctrl+Shift+D) відкриває зсув часу:
«+1 день», «+7 днів». Рухається лише годинник застосунку; збережені дані не змінюються.

## Офлайн і нагадування

Service worker — `apps/web/public/sw.js` (у `next dev` — `sw.js?dev`: лише нагадування, нічого не кешує; реєструє
`lib/offline.ts` з `components/shell/offline-support.tsx`). Сторінки — спершу мережа, без неї
збережена копія (ключ — шлях без параметрів); невідома сторінка без мережі — домашня сторінка
в мові застосунку, інакше проста сторінка «Немає мережі». Статичні файли (`/_next/static`,
`/_next/image`, шрифти, картинки) — спершу кеш. `/api/*` ніколи не кешується. Після кожного
відкриття застосунок просить worker зберегти головні вкладки та всі файли з їхнього HTML
(не частіше ніж раз на 6 год), тож кожна вкладка відкривається офлайн; готовність —
`<html data-offline="ready">`. Зміна логіки worker — нове імʼя кешу (`CACHE`).

Нагадування — Web Push без вмісту. Телефон сам вирішує, коли нагадати: коли чекатиме 15 слів
(ті, що чекають зараз, і ті, що настануть), але не раніше ніж за 1,5 год після виходу
(`nextReminderAt` у `lib/reminders.ts`), і при кожному виході зі сторінки повідомляє серверу лише
цей час (`/api/push`, `at`). Сервер (`/api/push/cron`) шле порожній push тим, чий час настав,
і більше не планує, доки застосунок не відкриють знову; worker пише текст сам, підписаний VAPID (`lib/push.ts`, без бібліотек), а worker пише текст сам зі
зведення в IndexedDB (`vocabx-sw` → `summary`: скільки слів чекає зараз і коли настануть
решта, тексти мовою застосунку), яке застосунок оновлює при відкритті й при кожному виході зі
сторінки. Push-сервіс тримає push для телефону без мережі до 20 год. Підписки — лист
«Нагадування» таблиці аналітики (`lib/reminder-store.ts`): адреса, увімкнено, мова, наступний
час (мс і дата); адреса,
що вже не діє (404/410), вимикається. `/api/push` приймає лише адреси push-сервісів браузерів.

На Vercel: додати `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` і `CRON_SECRET` (значення —
з `apps/web/.env`) та переконатися, що коренева тека проєкту — `apps/web` (там `vercel.json`).
Cron на тарифі Hobby — лише раз на день (16:00 UTC у `vercel.json`): цього мало, щоб
нагадування приходили вчасно. Потрібен зовнішній планувальник (наприклад, cron-job.org, безкоштовно)
кожні 15 хв: `GET https://<сайт>/api/push/cron` із заголовком `Authorization: Bearer <CRON_SECRET>`.
Пропозиція увімкнути нагадування — `components/shell/reminder-offer.tsx` (один раз, після
виходу з повторення з ≥ 10 відповідями, лише де нагадування підтримуються й вимкнені).

Перевірити нагадування — у панелі розробника: «Нагадування» показує його одразу (worker пише
текст зі зведення, як після push), «Push із сервера» проходить увесь шлях: `/api/push/test`
шле push на підписку цього телефона (не частіше ніж раз на 15 с).

У e2e service worker вимкнено (`serviceWorkers: 'block'`), крім `offline.spec.ts`.

## База даних

PostgreSQL на Neon, Drizzle (`apps/web/src/lib/db/schema.ts`, міграції в `apps/web/drizzle/`).
Застосунок працює на копії в браузері, а до бази звертається лише під час входу й синхронізації
(див. нижче). Кожен рядок для синхронізації має `server_seq` (його ставить тригер під час
оновлення) і `deleted_at` замість справжнього видалення.

- `pnpm db:check` — підключення й перелік таблиць.
- `pnpm db:generate` — нова міграція зі зміненої схеми.
- `pnpm db:migrate` — застосувати міграції; відмовляється працювати з базою, де є таблиці, але
  немає нашої історії міграцій.
- Міграцію, що видаляє колонки, застосовують лише після деплою коду, який їх уже не читає
  (інакше стара версія на Vercel упаде). Локальний `.env` дивиться в основну базу: `pnpm db:migrate`
  локально — це міграція продакшену. `0006` (прибирає `users.deleted_at`, `login_failures`,
  `locked_until`) — саме така, у файлі є SQL для відкату.
- `pnpm test:db` — серверні тести з базою (`src/**/*.db.test.ts`, не входять у `pnpm test`): на
  тестовій гілці Neon з `DATABASE_URL_TEST`. Скрипт `scripts/test-db.mjs` відмовляється працювати,
  якщо вона збігається з `DATABASE_URL`/`DATABASE_URL_DIRECT` (той самий рядок або той самий endpoint),
  спершу застосовує до неї міграції, прибирає з оточення пошту й `DATABASE_URL_DIRECT`, а тести
  працюють лише з адресами `*@db.vocabx.test` і видаляють їх після себе (`lib/db/testing.ts`).

Очищення (`/api/cleanup`, Vercel Cron щодня о 03:00 UTC, `CRON_SECRET`): видаляє те, чий строк
минув (строки — `lib/retention.ts`, затверджені в `docs/DATA_MAP.md` §6 і обіцяні на /privacy).
У Neon — один запит (`db.batch`), кожна інструкція не більше 2000 рядків за раз (решта — наступного
дня): надгробки 90 днів, непідтверджені акаунти 7 днів після листа, хеші посилань і паролі, що
чекали, 7 днів після закінчення посилання, лічильники лімітів, кеш перекладів 15 днів, тижні ліги
старші за 12 тижнів. У Google Sheets — рядки подій і сесій старші за 12 місяців, відгуки (обидві
таблиці) старші за 24 місяці, рядки «Нагадування»: порожні, вимкнені 30 днів, не оновлені 90 днів.
Відповідь і журнал — лише кількості. Пристрій, що не наздоганяв сервер понад 80 днів
(`FULL_RESYNC_MS` у `@vocabx/data`), завантажує все заново й прибирає те, чого на сервері вже
немає (якщо його не змінено тут), бо надгробка видаленого рядка могла зникнути.

Ліміти частоти запитів (`lib/rate-limit.ts`, таблиця `rate_limits`): лічильник на ключ із вікном,
що починається з першого запиту; перевірка — один upsert із `RETURNING`, разом зі своїм маршрутом
одним запитом до Neon (`db.batch`). Ключі містять лише HMAC (на `NEXTAUTH_SECRET`) адреси
відправника (IPv6 — мережа /64), акаунта чи пошти; рядки живуть до кінця вікна, кожна перевірка
прибирає до 20 рядків, що скінчилися понад годину тому. База — лише на рідкісних і дорогих
маршрутах (`translate`, реєстрація, новий пароль, вхід, `dev-unlock`, `feedback`) і на тих, що й
так відкривають базу (`sync`, `league`); без бази лічильник у памʼяті інстансу. `track`, `push` і
`push/test` базу не будять: їхній ліміт — `memoryLimiter` (лише в межах інстансу, до кроку 3.1).
Відповідь понад ліміт — 429 із `Retry-After` (`tooMany`).

Ліміти й обмеження даних (кроки 2.1b, 2.2):

| Маршрут     | Ліміт                                                   | Тіло, обсяг                |
| ----------- | ------------------------------------------------------- | -------------------------- |
| `sync`      | 300 за 10 хв і 1000 за годину на акаунт (до транзакції) | 4 МБ; квота рядків (нижче) |
| `league`    | 60 за 10 хв на акаунт                                   | 8 КБ                       |
| `feedback`  | 5 за 10 хв з адреси; 500 на добу для всіх               | 32 КБ                      |
| `track`     | 600 за 10 хв з адреси (памʼять інстансу)                | 64 КБ                      |
| `push`      | 30 за 10 хв з адреси (памʼять інстансу)                 | 2 КБ                       |
| `push/test` | 10 на годину з адреси і 1 за 15 с на підписку           | 2 КБ                       |

Тіло читає `readJson` (`lib/api-user.ts`): понад ліміт — 413 одразу, без читання до кінця. Квота
рядків акаунта на сервері — `SYNC_QUOTA` у `lib/sync-server.ts` (слів 20 000, колод 1 000, карток
20 000, відповідей 250 000); перевіряється перед записом, лише для таблиць, у які запит додає
рядки; коли таблиця повна — 413, і пристрій показує «сервер уже тримає весь обсяг» (`status:
'full'`). Час у запиті не пізніший за рік 3000 (`MAX_TIME_MS`), час відповіді довший за годину
зберігається як година, інакше — 400. Ліга: за добу (UTC) платять не більше `maxEventsPerDay`
(2000) відповідей (`packages/core/src/config/params.ts`).

Нові дані (таблиця чи колонка, ключ у браузері, кука, лист у таблицях Google, сторонній сервіс)
додаються рядком у `docs/DATA_MAP.md` у тій самій зміні; нове джерело контенту, графіки, шрифту
чи онлайн-сервісу — ще й у `docs/LICENSES.md`.

Схеми `auth` і `neon_auth` належать Neon. `reference/schema.sql` — давніший ескіз, не чинна схема.

## Вхід

NextAuth v4 і Google (`apps/web/src/lib/auth.ts`). Сесія — у підписаній cookie, тож база не
прокидається від відкриття сторінок. Без `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` і
`NEXTAUTH_SECRET` на час збірки картки акаунта в профілі немає.

В OAuth-клієнті (Google Cloud → APIs & Services → Credentials) для кожної адреси, де працює вхід,
потрібні Authorized JavaScript origin і redirect URI `<адреса>/api/auth/callback/google`.
`NEXTAUTH_URL` має збігатися з адресою, яку відкрито в браузері.

Вхід через email і пароль (`lib/email-accounts.ts`): пароль зберігається як scrypt-хеш, увійти можна
лише після переходу за посиланням із листа (`/api/account/verify`, токен діє добу, у базі лише його
хеш). У кожному листі одне посилання, і чинне лише посилання останнього листа. Пароль, обраний під
час реєстрації, чекає поруч зі своїм посиланням (`pending_password_hash`) і стає паролем акаунта
тільки через нього: повторна реєстрація непідтвердженої адреси не змінює пароль мовчки, а старий
лист не підтверджує новий пароль. Посилання входить лише в тому браузері, який зробив саме цю
реєстрацію (cookie-доказ `vocabx-email-proof`, шлях `/api/account`, зроблений із ключа цієї
реєстрації). «Надіслати ще раз» працює лише з того самого браузера.

Новий пароль (`/api/account/reset`): `{ email, locale }` — лист із посиланням
`/<мова>/profile#reset=<токен>` (токен після `#`, тож не потрапляє на сервер і в Referer; діє годину,
один раз); відповідь завжди 202, лист іде вже після відповіді (`after`), тож ні відповідь, ні час не
видають, чи є акаунт. `{ token, password }` — задає пароль, підтверджує адресу, знімає блокування й
входить: 204 або 410. Екрани: «Забули пароль?» у діалозі входу і форма нового пароля, яку
відкриває посилання (`components/account/account-links.tsx` читає `#reset=` і одразу прибирає його
з адреси).

У профілі, увійшовши (`components/account/change-*.tsx`): `GET /api/account` — `{ password, google }`.
Зміна пароля — `POST /api/account/password` `{ current, password }`: 204, 422 хибний поточний, 409
пароля немає (лише Google — тоді лист «Забули пароль?» на свою пошту), 429; посилання, що чекали,
перестають діяти. Зміна пошти — `POST /api/account/email` `{ email, password, locale }` → 202, лист
на нову адресу з `/<мова>/profile#email=<токен>&to=<адреса>`; у базі — хеш токена разом з адресою
(той самий `verify_token_hash`, тож нове посилання вбиває попередні, а адресу в посиланні не
підмінити). `{ token, email }` — зміна, підтверджена адреса, вхід з новою адресою: 204, 410, 409
(адресу встигли зайняти). Акаунт із Google тримає адресу Google (409). Адреса, що вже має акаунт,
листа не отримує, а відповідь та сама. Спроби з паролем: 10 за 15 хв на акаунт (`account-check`),
листи — у тих самих лімітах, що й реєстрація.

Реєстрація й вхід відповідають однаково для всіх адрес: невідома адреса й хибний пароль — однакове
`invalid` після тієї самої перевірки хешу. Ліміти входу (`checkLogin`): 30 спроб за 15 хв з однієї
адреси відправника (будь-які адреси пошти); 10 хибних паролів для однієї пошти з однієї адреси
відправника закривають її лише для цього відправника на 15 хв, 100 з усіх адрес — для всіх на
годину. Лічильники ведуться за HMAC пошти, тож невідома адреса закривається так само, і `limited`
нічого не каже про акаунт. Новий пароль листом або вдалий вхід знімають лічильники хибних паролів.
Колонки `login_failures`, `locked_until` більше не використовуються (прибрати окремою міграцією).

Реєстрація (і «надіслати ще раз») та запит нового пароля: по 10 на годину з однієї адреси
відправника, окремими лічильниками, ще до хешування пароля; разом — не більше `EMAIL_DAILY_LIMIT`
запитів на добу, що можуть надіслати лист (понад — 503). Google-вхід
приєднує акаунт із тією самою поштою; якщо її не було підтверджено, скидаються пароль, пароль, що чекав, і
посилання.

Кожен маршрут `/api`, що щось змінює (POST/DELETE), першим рядком перевіряє `crossSite(request)`
(`lib/api-user.ts`): запит зі сторінки іншого сайту (чужий `Origin` або `Sec-Fetch-Site: cross-site`)
отримує 403. Це другий захист після `SameSite=Lax`; `api-user.test.ts` перевіряє, що жоден маршрут
його не пропустив. `/api/auth/*` перевіряє next-auth.

`pnpm db:seed-test` створює 5 підтверджених акаунтів
`test1…5@vocabx.test` і друкує пароль.

## Синхронізація

Застосунок ніколи не чекає на сервер: він працює на копії в браузері, а `SyncJournal` запамʼятовує
id змінених рядків (не значення). Для того, хто не входив, нічого не записується й не надсилається.

Один запит `POST /api/sync` (`lib/sync-server.ts`) і читає, і пише, тож будить базу один раз:
пристрій каже, який останній `server_seq` бачив і що змінив. Якщо хтось записав пізніше, сервер
нічого не пише й віддає ці рядки; пристрій обʼєднує їх (`sync-merge.ts`) і повторює. Рядки одного
користувача йдуть по черзі (`pg_advisory_xact_lock`), тож номер ніколи не пропускає рядка.

Коли йде запит (`lib/sync.tsx`): відкриття застосунку (є що надіслати або минуло 5 хв), вихід із
повторення, згортання вкладки (є що надіслати, не частіше ніж раз на 2 хв), повернення (минуло
15 хв), поява мережі, раз на 10 хв у відкритій вкладці, кнопка в профілі. Значення сталих — там само.

Правила обʼєднання: відповіді не губляться ніколи; картка — від пізнішої відповіді; слово — новіше;
колода — новіша зі словами обох; особиста колода, «вивчені» й копія вбудованої колоди — одна на
користувача (лишається найстаріша); налаштування — цього пристрою; профіль і нагороди додаються. XP і
серії рахуються зі статистики, а вона — з відповідей, тож окремо не обʼєднуються.

Після виходу дані лишаються в браузері й не надсилаються; зміни запамʼятовуються на випадок
повернення в той самий акаунт. Інший акаунт: користувач вибирає, обʼєднати дані чи взяти лише його.
Скидання даних також виходить з акаунта; копія на сервері лишається. Видалення акаунта
(`DELETE /api/account`) прибирає з сервера все: усі таблиці посилаються на `users` з `ON DELETE
CASCADE`.

## Рейтинг

Ліги, групи до 10 учнів, тиждень від понеділка за UTC (`packages/core/src/league.ts`,
`lib/league-server.ts`). Сторінка закрита, доки учень не натисне кнопку (`AppSettings.leagueJoined`):
до того для рейтингу нічого не надсилається. Менше 4 учасників — ніхто не переходить; далі 30%
групи підвищуються й стільки ж опускаються (1 з 4, 3 з 10). Окремого щотижневого завдання немає:
тиждень закривається для учня, щойно він зʼявляється наступного разу.

Сторінка відкривається одразу з копії в браузері (`lib/league-cache.ts`) і оновлюється у фоні: лише
місця раз на 30 хв (раз на 5 хв, якщо учень щось повторив), імена й персонажі раз на добу, новим
тижнем, коли в групі новий учасник чи хтось змінив вигляд (сервер віддає відбиток `tag`). Зміну одягу
чи рамки застосунок надсилає сам за кілька секунд. Сталі — на початку `LeagueView`. Панель розробника відкриває
10 вигаданих учасників (`lib/league-demo.ts`, `?demo=1`) без жодного запиту.

Рамка персонажа (`AvatarFrame`): 7 світлих і 7 темних фонів, завжди доступних, 7 кольорів рамки;
градієнтні фони відкриваються разом із темами, градієнтні рамки — з лігою учня. Сервер показує
іншим рамку ліги лише тому, хто до неї дійшов. Картинки персонажів завжди мають `sizes` за
розміром на екрані: без нього маленька іконка вантажить картинку на всю ширину екрана.

Сервер не вірить числу XP з пристрою. `creditXp` рахує під час синхронізації, скільки відповідь
могла дати щонайбільше, і бере менше з двох значень; 0 за відповідь із майбутнього, раніше за вступ
чи початок тижня, швидшу за 400 мс, понад 40 за хвилину чи понад 3 за слово за день. Зарахований XP
лежить у `review_events.credited_xp`, тому скасована відповідь повертає рівно стільки. XP, рівень і
серії в самому застосунку лишаються локальними: їх можна підробити, але на рейтинг це не впливає.
Бота, що відповідає в людському темпі, так не виявити; його стримує лише денна межа XP.
